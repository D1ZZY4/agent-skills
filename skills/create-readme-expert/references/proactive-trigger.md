# Proactive Trigger

When to propose README creation or improvement without being asked, and when to stay quiet.

## When to act

- The repository has no README, or the README is clearly outdated.
- A user-facing workflow, installation path, public API, or CLI command changed.
- Installation or usage instructions are missing, wrong, or contradictory.
- Onboarding documentation would meaningfully reduce repeated questions.
- A project is being prepared for release, a demo, or an external handoff.

## When to stay quiet

- The README already exists and matches the current project state.
- The project is private or internal, and the audience has not requested documentation.
- The user explicitly asked to skip README work.

## Confidence rule

- Only propose README changes when the content can be verified against the actual project.
- Do not rewrite a README based on assumptions, memory, or generic templates.

## How to offer

Propose the change with the specific gap you found and the shape of the fix, so the user can
approve or redirect with one look. Recommend a targeted fix unless the existing structure
cannot represent the project accurately, in which case propose a rewrite.

## Release or update behavior

Suggest a README review when:

- a release introduces user-visible changes
- installation instructions change
- migration steps are required
